# Hackathon Presentation Playbook

Use this reference for short demo-day, judging, and project-showcase presentations. Treat event rules and the supplied judging rubric as authoritative.

## Time budgeting

Start with the event time limit, then reserve time for the live demo and transition pauses. A useful default for a 5-minute pitch is:

| Segment | Approximate share | Purpose |
|---|---:|---|
| Hook and problem | 15% | Make the pain and user concrete |
| Solution and product flow | 25% | Explain what was built and how it helps |
| Live demo | 30% | Show one complete user journey and outcome |
| Technical credibility | 15% | Explain the key implementation choice |
| Evidence, impact, and closing ask | 15% | Leave judges with proof and a memorable next step |

If the demo is excluded from the time limit, still design a clear handoff and return-to-deck moment. If the limit is under three minutes, reduce the deck to a hook, problem, solution, demo result, and close; move architecture to appendix.

## Narrative rules

- State the project’s value proposition in one sentence on the title slide.
- Describe the problem through a person, workflow, or consequence rather than an abstract market claim.
- Show the shortest complete product path: input, key action, and visible outcome.
- Explain one or two technical choices that create credibility or differentiation; do not present an inventory of tools.
- Connect evidence directly to the judging rubric: accuracy, speed, adoption, accessibility, novelty, feasibility, or impact.
- End with one explicit ask or next step: try it, scan a QR code, approve the prototype, support a pilot, or remember the team.

## Slide writing

Prefer one takeaway headline per slide. Use short labels, numbers, and captions around screenshots. Replace paragraphs with a sequence of claim, proof, and implication. Use large numerals only when they represent meaningful evidence; never invent traction or performance data.

## Demo resilience

For each critical live-demo moment, prepare a fallback visual containing:

1. The user action.
2. The relevant interface or system state.
3. The outcome or metric the judges should notice.

The fallback may be a screenshot sequence, a short embedded recording when supported, or a static “what would happen next” slide. Keep it visually consistent with the main deck and make the transition easy to execute. Never claim that a fallback screenshot is live evidence.

## Technical architecture

Use a simple diagram with no more than the components needed to explain the product’s differentiating path. Prefer a left-to-right or top-to-bottom flow with readable labels, one accent color for the active path, and a concise caption for the design tradeoff. Put APIs, framework names, or implementation details in a small but still legible supporting line or appendix when they are not central to judging.

## Rubric alignment

Before final delivery, map each judging criterion to at least one visible slide or speaking beat. If a criterion is not supported by evidence, do not hide the gap with decorative language; state the current status and the next validation step. Keep the rubric mapping in presenter notes or HTML comments rather than rendering internal process labels on the slide.

## Rehearsal checklist

- Can the first slide be understood in three seconds?
- Can the presenter complete the main story without the live network?
- Does the demo have a known starting state and a clear return-to-deck point?
- Can every architecture label be read from the back of a room?
- Is the closing ask explicit and actionable?
- Does the deck still communicate correctly with reduced motion and in a static PDF?
